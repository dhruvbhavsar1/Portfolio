PRIORITY PING — COMPLETE PROJECT EXPLANATION
==============================================

Project Name:
Priority Ping

Project Type:
Android application for priority/important notifications.

Purpose:
Priority Ping is an Android notification-management application designed to make sure
important notifications are not easily missed. The app monitors incoming notifications,
checks whether a notification belongs to an application/contact that the user has marked
as important, and then gives that notification special treatment.

The main problem it solves:
Android can silence or reduce the visibility of notifications because of silent mode,
Do Not Disturb (DND), notification-channel settings, app settings, or user attention.
Priority Ping is designed around the idea that selected notifications should receive
higher priority and stronger user attention.

IMPORTANT TECHNICAL NOTE:
The application does NOT simply "hack" Android's DND system. It works through Android's
supported notification and policy-access mechanisms. Depending on Android version,
OEM/device restrictions, notification-channel configuration, and granted permissions,
the exact behavior can differ.

--------------------------------------------------
3. HOW THE APP ACTUALLY WORKS
--------------------------------------------------

STEP 1 — USER OPENS THE APP
The user opens Priority Ping and configures which applications or contacts should be
treated as important.

Examples:
- WhatsApp
- Instagram
- Snapchat

The project was designed around selected applications and specific sender/profile
information.

STEP 2 — USER CONFIGURES PRIORITY
The user can define which notifications are important.

For example:
WhatsApp:
    Contact = "Rahul"
    Priority = High

Instagram:
    Profile/user = selected profile
    Priority = High

Snapchat:
    User/profile = selected profile
    Priority = High

The exact configuration depends on the implementation.

STEP 3 — NOTIFICATION ACCESS
Android's NotificationListenerService is used.

The user must manually grant Notification Access to Priority Ping from Android settings.

This permission allows the application to receive callbacks when notifications are posted,
removed, or changed.

The app does NOT need to continuously poll every application.

Instead, Android provides notification events to the listener service.

STEP 4 — NOTIFICATION ARRIVES
Suppose WhatsApp receives a message.

Android creates a notification.

The NotificationListenerService receives the notification event.

Conceptually:

onNotificationPosted(statusBarNotification)

The service can inspect the notification package and its extras.

STEP 5 — IDENTIFY THE SOURCE APP
The notification contains information about which application generated it.

The package name can be used.

Examples:
WhatsApp:
com.whatsapp

Instagram:
com.instagram.android

Snapchat:
com.snapchat.android

Priority Ping uses the package/application identity to determine which rule should be
applied.

STEP 6 — EXTRACT NOTIFICATION INFORMATION
The Notification object contains extras.

The implementation can read values such as:

android.title
android.text

The title commonly contains a sender/contact/application-generated title.

The text commonly contains the notification message or preview.

Example conceptual notification:

Package:
com.whatsapp

Title:
Rahul

Text:
"Call me when you are free"

Priority Ping can use this information for matching.

STEP 7 — MATCH THE NOTIFICATION
The notification is passed through the matching logic.

The matching process is conceptually:

1. Check application package.
2. Find rules configured for that application.
3. Extract sender/title/profile information.
4. Compare it against configured priority contacts/users.
5. Determine priority level.
6. Trigger appropriate handling.

Example:

Incoming:
package = com.whatsapp
title = Rahul

Configured:
package = com.whatsapp
contact = Rahul
priority = HIGH

Result:
MATCH

If:

package = com.whatsapp
title = Unknown Person

and no matching rule exists:

Result:
NO MATCH

STEP 8 — PRIORITY HANDLING
When a notification matches a priority rule, the app attempts to give it stronger
attention using Android's supported notification/policy mechanisms.

Possible mechanisms include:
- Higher notification importance where applicable
- Custom vibration
- Notification policy access / DND-related handling
- Re-posting or creating a priority notification where appropriate
- Custom notification sound where permitted
- Other notification behavior supported by the Android version

The exact behavior depends heavily on Android's notification and DND restrictions.

--------------------------------------------------
5. WHY NOTIFICATIONLISTENERSERVICE WAS USED
--------------------------------------------------

A normal Activity cannot reliably monitor all notifications while the app is closed.

The NotificationListenerService is specifically designed for notification access.

Advantages:
- Android manages the service lifecycle.
- It receives notification events.
- It can work while the application UI is not open.
- It can inspect notification metadata that Android exposes through the listener API.

This is the core reason this architecture was selected.

--------------------------------------------------
8. PRIORITY LEVEL MODEL
--------------------------------------------------

The project included a PriorityLevel model.

A priority level represents how important a matched notification is.

Conceptually:

LOW
MEDIUM
HIGH

or equivalent levels depending on the implementation.

The priority model separates the rule:

"Who/what is important?"

from the behavior:

"What should happen when it is important?"

This makes the architecture easier to extend.

For example:

PriorityLevel.HIGH
    -> stronger vibration
    -> priority handling

PriorityLevel.MEDIUM
    -> normal custom vibration

PriorityLevel.LOW
    -> lighter handling

--------------------------------------------------
10. SOUND AND DND
--------------------------------------------------

One of the important goals of the project was to make selected notifications noticeable
even when the phone is quiet.

However, Android does not allow an ordinary application to arbitrarily bypass all system
silencing rules.

The supported architecture involves Android notification policy access and notification
settings.

DND-related behavior may require the user to grant Notification Policy Access.

The application can then work within Android's policy APIs.

Important distinction:

Notification Access
    Allows Priority Ping to observe notifications.

Notification Policy Access
    Allows the app to interact with supported Do Not Disturb / interruption policy
    controls.

These are different permissions/access mechanisms.

The user must explicitly grant the relevant access from Android settings.

Even with policy access, Android/OEM restrictions can affect behavior.

12. NOTIFICATION CHANNELS
--------------------------------------------------

Modern Android uses notification channels.

A notification channel can control:
- Importance
- Sound
- Vibration
- Visibility
- Other notification behavior

A major limitation is that applications cannot always override user-modified channel
settings.

Therefore, if the project creates or manages a priority channel, the user/device's
channel configuration still matters.

Example:

priority_channel
    importance = HIGH

The actual behavior can still depend on:
- User settings
- Android version
- OEM skin
- Device sound mode
- DND policy
- Channel settings

--------------------------------------------------
18. WHY THE APP DOES NOT NEED A SERVER
--------------------------------------------------

The core Priority Ping functionality can operate locally on the Android phone.

The notification event already exists on the device.

The application does not need to send the notification to a remote server to decide
whether it is important.

Advantages:
- Lower latency
- Works without internet for core processing
- Better privacy
- No backend infrastructure
- No server cost
- Faster matching

Room also provides local persistent storage.

--------------------------------------------------
19. PRIVACY CONSIDERATIONS
--------------------------------------------------

Notification content can be sensitive.

Because the app observes notification information, it should:
- Process data locally when possible.
- Avoid unnecessary network transmission.
- Avoid logging message contents.
- Protect stored priority configuration.
- Request only necessary permissions.
- Explain why Notification Access is required.

The project architecture is naturally suited to local processing.

--------------------------------------------------
20. ANDROID SECURITY MODEL
--------------------------------------------------

Priority Ping operates inside Android's permission/security model.

Important security boundaries:

Notification Access:
    User grants access.

Notification Policy Access:
    User grants policy access.

Notification channels:
    Controlled by Android and user settings.

DND:
    Controlled by Android's interruption policy.

Sound:
    Controlled by system volume/modes and notification configuration.

OEM restrictions:
    Manufacturers may change background-service behavior.

Therefore the app cannot guarantee identical behavior on every Android phone.

--------------------------------------------------
21. IMPORTANT LIMITATIONS
--------------------------------------------------

1. Android version differences
Notification APIs and restrictions change across Android releases.

2. OEM differences
Samsung, Xiaomi, OnePlus, Vivo, Oppo, etc. can apply additional background restrictions.

3. Notification parsing differences
WhatsApp, Instagram, Snapchat and other applications do not expose notification data
in exactly the same way.

4. Notification grouping
Multiple messages may be grouped into one notification.

5. Private/hidden notification content
Lock-screen privacy or application behavior can limit available text.

6. User settings
Users can change channel importance, sound, vibration, DND rules, etc.

7. DND restrictions
The application cannot arbitrarily defeat Android's security model.

8. Battery optimization
Some manufacturers aggressively restrict background processes.

9. App updates
If another app changes its notification format, matching logic may need updates.

27. MATCHING ENGINE
--------------------------------------------------

A clean matching engine should conceptually do:

Input:
NotificationData

Output:
PriorityMatch or NoMatch

NotificationData:
- packageName
- title
- text
- timestamp
- notification key
- other available metadata

Rule:
- packageName
- target identifier
- priority
- enabled

Matching:

if rule.enabled
and rule.packageName == notification.packageName
and target matches notification title/content:

    return matching priority

else:

    no match

This separation makes the service easier to maintain.

31. HOW TO EXPLAIN THIS PROJECT TO A FACULTY
--------------------------------------------------

Short technical explanation:

"Priority Ping is a Kotlin-based Android application that monitors incoming
notifications using NotificationListenerService. The user configures important
applications or contacts, and the service receives notification events from Android.
We extract the package name, title and text from the notification extras and compare
them with locally stored priority rules. For matching notifications, the app applies
priority handling such as custom vibration and supported notification/policy behavior.
We use Room over SQLite to persist the priority configuration locally. For DND-related
functionality, we use Android's Notification Policy Access mechanisms rather than
trying to bypass Android security."

If asked:
"How does it work when the app is closed?"

Answer:
"The UI does not need to remain open. NotificationListenerService is an Android
system-managed service that receives notification events. So when a notification is
posted, Android invokes the listener and our matching logic processes it."

If asked:
"How do you know the notification is from WhatsApp?"

Answer:
"We use the notification's source package name, for example com.whatsapp."

If asked:
"How do you know who sent it?"

Answer:
"We read the notification extras such as android.title and android.text and match
the exposed sender/title information against the user's configured priority rule.
The exact data available depends on the source app and Android version."

If asked:
"How did you bypass DND?"

Better technical answer:
"We did not bypass Android security. We used Android's supported Notification Policy
Access and notification APIs. The user grants the required access, and the app applies
priority behavior within the restrictions imposed by Android and the device."

If asked:
"Why Room?"

Answer:
"Room provides a structured abstraction over SQLite for storing priority rules and
configuration locally."

--------------------------------------------------
34. FINAL PROJECT SUMMARY
--------------------------------------------------

Priority Ping is an Android notification-prioritization application built with Kotlin.
Its central component is NotificationListenerService, which receives notification
events from Android. The application identifies the source package, extracts available
notification information, and compares it against user-defined priority rules.

The configuration is stored locally using Room/SQLite. When a notification matches a
priority rule, the application performs supported priority notification behavior such
as custom vibration and notification/policy handling.

The application is intentionally local-first and does not require a server for its core
notification processing. It demonstrates Android background services, notification
APIs, special permissions, local databases, event-driven architecture, and system-level
integration.

The most important technical point is that Priority Ping works WITH Android's supported
APIs and permissions; it should not be described as an unrestricted DND bypass.
