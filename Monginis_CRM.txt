MONGINIS CRM — COMPLETE PROJECT DOCUMENTATION
=================================================

Project Name:
Monginis CRM (CakeCRM)

Project Type:
Private mobile Customer Relationship Management (CRM) application for a Monginis cake shop/business owner.

Purpose:
The application is designed to help a cake shop owner manage customer information, birthdays, customer preferences, VIP/new-customer status, reminders, and communication from one private mobile application.

The application is intended to be installed as a private APK on the owner's Android phone. It is not a customer-facing application and the admin side is not intended to be published publicly.

------------------------------------------------------------
1. HIGH-LEVEL OVERVIEW
------------------------------------------------------------

Monginis CRM is an offline-first Flutter mobile application.

The main idea is:

    User
      |
      v
    Flutter UI
      |
      v
    Provider / Application State
      |
      +----------------------+
      |                      |
      v                      v
   Hive Local            Firebase
   Storage               Firestore
      |                      |
      +----------+-----------+
                 |
                 v
          Sync / Backup Logic

The application is designed so that the local device remains the primary working environment while Firebase Firestore can provide cloud backup/synchronization.

This architecture is important because the CRM should remain usable even when the internet connection is unavailable.

The application stores customer records locally, displays them quickly from local storage, and can synchronize/backup data with Firestore when required.

11. NOTIFICATION SYSTEM
------------------------------------------------------------

The CRM uses local notifications for birthday reminders.

A three-alert strategy was considered:

- 7 days before
- 1 day before
- Day of birthday

For efficiency, the design was later simplified toward a single daily reminder around 8:00 AM.

The purpose is to avoid creating excessive notification schedules for every customer.

Instead, the application can perform a daily check:

    8:00 AM
       |
       v
    Read local customers
       |
       v
    Find relevant birthdays
       |
       v
    Build reminder
       |
       v
    Local notification

This approach reduces background scheduling complexity.

A Test Notification function/button was also discussed so the owner can verify that notifications work.

13. OFFLINE-FIRST ARCHITECTURE
------------------------------------------------------------

Offline-first means the application does not depend on an internet connection for normal CRM operation.

Primary flow:

    User
      |
      v
    Flutter UI
      |
      v
    Provider
      |
      v
    Hive
      |
      v
    Local data

Internet is only needed for operations that require cloud services, such as synchronization or backup.

This means:

- Customer list can load offline
- Customer details can load offline
- Customer creation can work offline
- Customer editing can work offline
- Birthday calculations can work offline
- Dashboard statistics can work offline

This is especially useful for a shop environment where connectivity can be unreliable.

------------------------------------------------------------
14. WHY HIVE?
------------------------------------------------------------

Hive is used as the local database/storage layer.

Advantages for this CRM:

- Fast
- Lightweight
- Local
- Works without internet
- Suitable for structured local data
- Good fit for Flutter
- Reduces Firestore reads
- Improves startup and screen performance

The application can keep the working customer dataset in Hive.

Instead of:

    Open screen
       |
       v
    Firestore query
       |
       v
    Display

the preferred approach is:

    Open screen
       |
       v
    Hive
       |
       v
    Display immediately

Cloud synchronization can happen separately.

------------------------------------------------------------
15. FIREBASE FIRESTORE
------------------------------------------------------------

Firestore is used as the cloud database / backup layer.

Its role is not necessarily to serve every UI screen directly.

A better architecture is:

    Local database = primary working copy

    Firestore = cloud backup / synchronization source

This helps reduce:

- Firestore reads
- Firestore writes
- Network dependency
- Screen loading time

Firestore is useful when:

- Data needs cloud backup
- The owner changes devices
- Data needs synchronization
- A central cloud copy is required

------------------------------------------------------------
16. FIRESTORE READ OPTIMIZATION
------------------------------------------------------------

One major optimization discussed for the CRM is avoiding repeated reads.

Bad architecture:

    Every screen
        |
        v
    Firestore query
        |
        v
    Display data

This can produce unnecessary reads.

Better architecture:

    Firestore
        |
        v
    Sync once / when changed
        |
        v
    Hive
        |
        v
    Provider
        |
        v
    UI

The UI then reads local data.

This dramatically reduces unnecessary Firestore activity.

------------------------------------------------------------
17. PRODUCT CATALOG OPTIMIZATION
------------------------------------------------------------

The CRM/application also considered product catalog data.

Product information can be cached locally.

Instead of downloading all product information repeatedly:

    App Start
       |
       v
    Check catalog version
       |
       v
    Has catalog changed?
       |
      / \
     No  Yes
     |    |
     v    v
   Hive  Firestore
          |
          v
        Update Hive

A catalog version/version ID can be stored in Firestore.

If the local version matches the cloud version:

    No catalog download required.

If the version differs:

    Download updated catalog
    Save to Hive
    Update local version

This is a major read-optimization strategy.

------------------------------------------------------------
18. PRODUCT DATA VS STOCK DATA
------------------------------------------------------------

Product information and stock information should be treated differently.

Product information changes less frequently.

Examples:

- Product name
- Description
- Price
- Image
- Category

Stock can change frequently.

Therefore:

    Product catalog
        -> Cache locally

    Stock
        -> Fetch/update when required

This prevents frequently changing stock information from unnecessarily invalidating the entire product catalog cache.

------------------------------------------------------------
19. IMAGE STORAGE / CLOUDINARY
------------------------------------------------------------

Cloudinary was considered for product images.

The idea is:

    Product metadata
        -> Firestore

    Product image
        -> Cloud image storage/CDN

    Local application
        -> Cache image / metadata when appropriate

This prevents Firestore from being used as a heavy image-storage system.

------------------------------------------------------------
20. ORDER HISTORY STRATEGY
------------------------------------------------------------

Order data can become large over time.

The proposed architecture was:

    Recent orders
        -> Firestore

    Older orders
        -> Archive/export locally

For example, the system can keep roughly the latest 2–3 months of active order history in Firestore.

Older data can be archived into:

- Excel
- PDF

After the administrator has downloaded/archived older records, those old Firestore records can be removed if the business workflow allows it.

This reduces long-term cloud storage and database usage.

------------------------------------------------------------
21. FIRESTORE FREE-TIER AWARENESS
------------------------------------------------------------

The architecture was designed with Firestore usage limits/cost awareness in mind.

Important resources include:

- Document reads
- Document writes
- Stored data
- Network usage

The exact Firebase limits/pricing can change, so production deployments should always use the current Firebase documentation.

The application architecture reduces usage by:

- Caching locally
- Avoiding repeated reads
- Synchronizing only when necessary
- Separating frequently changing data
- Using catalog versions
- Archiving old orders

30. MONTHLY SYNC / FINAL PRODUCT CONCEPT
------------------------------------------------------------

A monthly synchronization/backup concept was discussed for the final CRM product.

The core idea is to keep the application efficient and locally usable while periodically ensuring cloud data is synchronized/backed up.

The exact production behavior can be implemented as a controlled synchronization process rather than constantly syncing every operation.

A robust version can support:

    Local changes
        |
        v
    Pending sync
        |
        v
    Sync process
        |
        v
    Firestore
        |
        v
    Sync confirmation

A scheduled monthly full reconciliation can also be used as an integrity check, while normal changes can be synchronized incrementally.

Important distinction:

- Incremental sync = changed records
- Full reconciliation = verify local/cloud consistency

For a final production CRM, incremental synchronization should generally be preferred for normal operations, with periodic reconciliation for safety.

31. SYNC CONFLICTS
------------------------------------------------------------

If the CRM eventually runs on multiple devices, conflicts can occur.

Example:

Device A:
    Customer phone = 1111

Device B:
    Customer phone = 2222

Both modify the same customer.

The system needs a conflict policy.

Possible approach:

    updatedAt comparison

The newest valid update wins.

For more advanced systems:

    version numbers
    conflict logs
    manual conflict resolution

For a single-device private CRM, conflict complexity is much lower.

The application can check network connectivity.

Internet unavailable does NOT mean CRM unavailable.

Instead:

    Internet ON
       -> Local CRM + cloud sync

    Internet OFF
       -> Local CRM only

This is one of the most important properties of the offline-first design.

33. SECURITY
------------------------------------------------------------

Security is important because the CRM contains customer information.

Important areas:

1. Firebase Authentication
2. Firestore Security Rules
3. No public read/write rules
4. Secure API/configuration
5. Local storage protection
6. Access control
7. Data backup
8. Device-level security

A previously discussed insecure Firestore rule such as:

    allow read, write: if true;

must NOT be used in production.

That rule effectively allows unrestricted access and is unsuitable for a real customer database.

    State
    Local Storage
    Cloud Storage
    Synchronization
    Services

Avoid:

      -> Repository

- Easier to scale

51. CURRENT ARCHITECTURAL PHILOSOPHY
------------------------------------------------------------

The CRM should NOT be treated as:

    "A Flutter UI connected directly to Firestore."

It should be treated as:

    "An offline-first business application with
     local-first data, controlled cloud synchronization,
     efficient caching, and business-specific services."

Core rule:

    LOCAL FIRST
        +
    CLOUD BACKUP/SYNC
        +
    LOW DATABASE READS
        +
    SIMPLE USER EXPERIENCE

52. FINAL SUMMARY
------------------------------------------------------------

Monginis CRM is a private Flutter-based CRM for a Monginis cake shop/business owner.

The application manages customers and birthday-related business information.

Flutter provides the mobile UI.

Provider manages application state.

Hive provides fast local/offline storage.

Firebase Firestore provides cloud storage, backup, and synchronization.

Local notifications provide birthday reminders.

WhatsApp integration lets the owner contact customers without building a separate messaging system.

The application is designed to continue working without internet access.

Cloud synchronization is separated from normal UI operation so the application does not need to query Firestore every time a screen opens.

Product data can be cached locally and refreshed using a catalog version system.

Older order information can be archived to reduce cloud storage.

Security must be handled through authentication and restrictive Firestore rules rather than public read/write permissions.

The final architecture is therefore:

    Flutter UI
        |
    Provider
        |
    Repository
        |
    +-----------+
    |           |
    Hive     Sync Service
                |
             Firestore

with supporting services for:

- Notifications
- WhatsApp
- Connectivity
- Product catalog
- Orders
- Authentication
- Cloud synchronization

This architecture is suitable as the foundation for a real private CRM product rather than only a UI demo.
