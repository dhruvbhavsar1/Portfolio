CHARITY APP — COMPLETE ARCHITECTURE & DATA FLOW DOCUMENT
============================================================

Document purpose
----------------
This document describes the Charity App architecture, technology stack,
data flow, storage model, Firebase usage, caching strategy, product flow,
order flow, authentication, media handling, optimization strategy, and
important architectural rules.

IMPORTANT:
This document distinguishes between:
1. Architecture/features already discussed as part of the current app.
2. Optimization ideas that were planned/discussed but must not be assumed
   to be fully implemented unless verified against the latest source code.

============================================================
1. APPLICATION OVERVIEW
============================================================

The Charity App is a Flutter mobile application backed primarily by Firebase.

The high-level architecture is:

                    +---------------------+
                    |     Flutter App     |
                    |       Android       |
                    +----------+----------+
                               |
              +----------------+----------------+
              |                |                |
              v                v                v
       Firebase Auth    Cloud Firestore    Storage/
                                           Image Service
              |                |                |
              +----------------+----------------+
                               |
                         App State / Cache
                               |
                    +----------+----------+
                    |                     |
                Provider              Hive /
              State Management       Local Cache


Core architectural principle:

Firebase is the cloud source of truth for shared application data.
Flutter is the application/UI layer.
Provider manages runtime state.
Hive/local storage is used for persistent caching and offline-oriented
behavior.
Media is handled separately from normal database documents.

Package responsibilities:

firebase_core
-------------
Initializes Firebase inside the Flutter application.

firebase_auth
-------------
Handles user authentication and authentication state.

cloud_firestore
---------------
Cloud NoSQL database used for shared application data such as:
- users
- products
- orders
- configuration/application data

firebase_storage
----------------
Used for file/media storage where applicable.

provider
--------
Runtime state-management layer.
Providers expose application data to screens/widgets and notify the UI
when data changes.

hive
----
Local persistent storage/cache.
Useful for:
- product catalog caching
- offline data
- persistent local state
- reducing repeated Firestore reads

shared_preferences
------------------
Small key/value local storage.
Suitable for:
- flags
- simple settings
- first-launch state
- version values
- lightweight preferences

path_provider
-------------
Provides application/device filesystem paths.

connectivity_plus
-----------------
Detects network connectivity changes.
It should be treated as a connectivity hint, not absolute proof that
Firebase is reachable.

cached_network_image
--------------------
Displays remote images while providing image caching to reduce repeated
image downloads.

image_picker
------------
Selects images from the device.

flutter_image_compress
----------------------
Compresses images before upload to reduce file size, bandwidth and storage.

flutter_dotenv
--------------
Loads configuration/environment values.
IMPORTANT: mobile application environment values are not a true secret store,
because values shipped inside an APK can potentially be extracted.

http
----
Used for HTTP requests where required.

intl
----
Date/number/local formatting.

pdf
---
Creates PDF documents/reports.

printing
--------
Print/share/save PDF output.

url_launcher
------------
Opens external URLs/app links such as websites, WhatsApp links, phone links,
or payment/UPI-related intents where applicable.

shimmer
-------
Loading placeholders while data is being fetched.

badges
------
UI badges and indicators.

The important separation is:

UI should display data.
Provider should manage runtime state.
Services/repositories should perform data operations.

 |                        |

 |

If:

- fetch/update required data
- update local Hive cache
- use updated local catalog

============================================================
14. PRODUCT DATA VS STOCK DATA
============================================================

Product catalog data and stock data should not necessarily have the same
refresh policy.

Product catalog:
- name
- description
- image
- category
- relatively stable price information

These can be cached aggressively.

Stock:
- available quantity
- rapidly changing inventory information

Stock may need more frequent refreshes because stale stock can cause
incorrect availability.

Therefore a possible optimized strategy is:

Product catalog
    |
    v
Longer local cache

Stock
    |
    v
More frequent refresh / validation


The exact refresh policy depends on the business requirements.

============================================================
15. HIVE ARCHITECTURE
============================================================

Hive is intended to act as persistent local storage/cache.

Provider and Hive have different purposes.

Provider:
- runtime application state
- fast access while the app is running
- UI notification/rebuild

Hive:
- persistent local data
- survives application restart
- cached product data
- offline-oriented access


Example:

Firestore
    |
    v
Provider
    |
    v
Hive


When the app is reopened:

Hive
 |
 v
Provider
 |
 v
UI


Hive should be treated as a cached/local representation of appropriate data,
not automatically as the authoritative source for shared cloud data.

19. WHY NOT LOAD EVERYTHING AT STARTUP
============================================================

Bad pattern:

App starts
 |
 +-- Load all users
 +-- Load all products
 +-- Load all orders
 +-- Load all reports
 +-- Load everything
 |
 v
Finally show Home


Problems:
- slow startup
- unnecessary Firestore reads
- unnecessary network traffic
- increased Firebase usage
- higher cost
- larger memory usage


Better pattern:

App starts
 |
 v
Load required data
 |
 v
Show UI
 |
 v
Load additional data when required

24. ORDER ITEMS
============================================================

 |     +-- quantity
 |     +-- price
 |     +-- other required snapshot information

 +-- status
 +-- createdAt


IMPORTANT:
An old order should not depend entirely on today's product document.

Example:

the order was created.

Therefore order items should preserve the relevant order-time snapshot
information.

28. ORDER READ OPTIMIZATION
============================================================

Orders can become much larger than the product catalog.

Example:

500 products may be stable.

10,000+ orders may accumulate over time.

Downloading all orders every time is inefficient.

Preferred techniques:
- filters
- date ranges
- pagination
- limits
- appropriate Firestore indexes
- loading only required records


Bad:

Admin opens orders
 |
 v
Download every order ever created


Better:

Admin opens orders
 |
 v
Load recent/required records
 |
 v
Pagination/date filters
 |
 v
Load more only when needed

31. FIRESTORE SECURITY
============================================================

A major security principle:

DO NOT rely only on hiding UI buttons.

For example, this type of broad rule is unsafe for production:

allow read, write: if true;


Security must be enforced at the backend/Firestore rule level.

Conceptual permissions:

User:
- read allowed personal data
- create allowed orders
- read own orders
- cannot arbitrarily modify admin/product data

Admin:
- manage products
- manage orders
- manage allowed users

Super Admin:
- broader/full administrative permissions


Exact Firestore security rules must be checked against the current project
before deployment.

============================================================
44. FIRESTORE READ OPTIMIZATION
============================================================

The central optimization principle is:

DO NOT READ DATA THAT THE USER DOES NOT NEED.

Examples:

Bad:
- download all products on every screen
- download all orders for every user
- repeatedly request unchanged data

Better:
- cache stable catalog data
- check versions
- query only required orders
- paginate large lists
- separate rapidly changing data such as stock
- load data when required
- keep frequently used data in memory
- persist useful stable data locally


============================================================
45. FIRESTORE COST MODEL — WHY OPTIMIZATION MATTERS
============================================================

Firestore usage is affected by document reads, writes, storage and other
Firebase services.

A simple conceptual problem:

1000 users
x
500 product documents
=
500,000 document reads

If the entire product catalog were unnecessarily fetched repeatedly by
many users, reads can grow rapidly.

Therefore caching is important.

The optimization goal is not merely:
"make Firebase faster."

It is:
"avoid unnecessary network operations and unnecessary document reads while
maintaining correct data."

48. ARCHITECTURAL RULES FOR FUTURE DEVELOPMENT
============================================================

Rule 1:
Do not put repeated Firestore queries directly inside UI widgets.

Preferred:
UI -> Provider -> Service/Repository -> Firebase/Hive


Rule 2:
Keep models responsible for converting data into structured objects.


Rule 3:
Keep Firebase as the cloud source of truth for shared data.


Rule 4:
Treat Hive as a local cache/local persistence layer unless the specific
feature is explicitly designed for local-only data.


Rule 5:
Do not cache rapidly changing data indefinitely.


Rule 6:
Do not download entire large collections when only a small subset is needed.


Rule 7:
Use pagination/limits/date filtering for large order collections.


Rule 8:
Do not rely on UI hiding for security.


Rule 9:
Enforce authorization through Firebase/Firestore security rules.


Rule 10:
Do not place real secrets inside a mobile application's client-side
environment configuration.


Rule 11:
Do not delete old cloud data until a verified archive/backup process exists.


Rule 12:
Keep product catalog caching and stock freshness as separate concerns.

50. ONE-SENTENCE ARCHITECTURE SUMMARY
============================================================

The Charity App is a Flutter/Firebase mobile application where Firebase
Authentication manages identity, Cloud Firestore stores shared application
data such as users, products and orders, Provider manages runtime state,
Hive/local storage provides persistent caching and offline-oriented access,
media services handle images/files, and the UI consumes structured models
through a service/data layer rather than directly depending on raw Firestore
documents.


============================================================
51. SHORT EXPLANATION FOR AN AI CODING AGENT
============================================================

When modifying this project, understand it as follows:

- Flutter/Dart is the client application.
- Firebase Authentication handles identity.
- Firestore is the main cloud database.
- Firebase Storage is used for files/media where configured.
- Provider manages application state.
- Hive is the local persistent cache/storage layer.
- SharedPreferences is for small local key/value settings.
- Products are relatively stable catalog data and should be cached efficiently.
- Orders are dynamic data and should be queried carefully.
- Product images should use caching.
- Product catalog and stock should not automatically use the same freshness
  strategy.
- UI should not repeatedly access Firestore directly.
- Use models for structured product/order/user data.
- Use services/repositories for database operations.
- Use providers to expose data to the UI.
- Use Firestore security rules for authorization.
- Do not assume planned catalog-versioning, product-change-ID or archival
  features are already implemented without verifying source code.
- Avoid unnecessary Firestore reads and writes.
- Preserve order-time product information so historical orders remain correct.
- Prefer loading only the data needed for the current screen.
- Use local cache when appropriate to improve startup/offline behavior.
